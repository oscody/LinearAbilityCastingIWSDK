## 1. What the source actually is

~20,900 lines of hand-written JS across 60 live modules (plus `src/archive/`, which
nothing imports and which Vite never bundles). Three.js r185 + lil-gui. No framework,
no ECS, no TypeScript.

The interaction is one loop: select an ability slot (Q/E/R/F/V/X), swing a ground
indicator with the mouse, click to fire. Six abilities — `ice`, `thunder`, `meteor`,
`beam`, `snare`, `glacier` — four aimed as a line, two (`snare`, `glacier`) as a
ground-targeted circle.

The architecture is unusually clean and that is what makes this port tractable:

- **`config/settings.js` (1,896 lines) is the API.** Every system *samples* settings
  each frame; nothing copies a value at spawn time. That is what makes the live
  editor work, and it means the data model ports untouched.
- **`App.js` builds subsystems and orders per-frame updates. No subsystem reaches
  back into App.** Dependencies flow one way, through a plain context object.
- **Everything is pooled.** `AbilityManager` pools per type, `LightPool` parks six
  point lights at zero intensity forever, particles are shared systems. Nothing is
  constructed during a cast.

That third point matters more than it sounds: the project's existing discipline
already matches the IWSDK rule "never allocate in `update()`".

### Draw-call budget the source reports

| State | Draw calls | Live particles |
|---|---|---|
| Idle | 32 | — |
| Full ice field standing | ~69 | ~1150 |
| Bolt in the air | ~49 | — |
| Snare with cage + field | ~45 | ~480 |
| Four concurrent casts (pool ceiling) | ~186 | — |

Measured on desktop, one view, pixel ratio capped at 1.75. **Quest 3 renders two
views at 72–90 Hz on an 11–14 ms budget.** Treat every number above as needing to
roughly halve. See §6.

**The one mandatory edit across all of them:** `import { … } from 'three'` must become
`from '@iwsdk/core'`. This is not cosmetic — importing `three` directly in an IWSDK
project creates a second Three instance and produces subtle, silent breakage. It is a
mechanical sweep across ~50 files. The single documented exception is
`import type { GLTF } from 'three/addons/…'`.

**Language:** the target scaffold is TypeScript. Converting 20k lines of untyped JS is
not the point of this port. Recommend enabling `allowJs` in `tsconfig.json` and landing
these modules as `.js`, converting opportunistically later. New IWSDK glue code (systems,
components) is written in TS.

### 2c. The post-processing stack: blocked, not cut

`postprocessing/PostProcessing.js` (198) + `GradeShader` + `DistortionShader`, and the
depth prepass that feeds `frame.uSceneDepth`.

**Why it can't come across as-is:** `EffectComposer` renders the scene into its own render
targets and then blits a fullscreen quad. A WebXR session requires rendering into the
session's framebuffer through the `ArrayCamera`, once per eye. The two models are
incompatible, and there is no IWSDK post-processing pipeline to hook into (I checked the
API surface — none exists).

**That is a "how", not a "whether" (D2).** Every pass below stays a requirement. None of
them is being cut from the design; they are blocked on the same missing capability, and
they come back together the day we solve it.

| Pass | What it does | Why it matters |
|---|---|---|
| `UnrealBloomPass` | Bloom, driven by `settings.global.glow` | Every ability's emissive palette was authored expecting bloom to smear it. Without it the VFX read flat and dim. |
| `GradeShader` | Vignette, contrast, saturation, temperature, lift/gain, grain, screen flash | The stage's whole colour identity. `ScreenFlash` is also a gameplay beat — impacts punch the screen. |
| `DistortionShader` | Screen-space refraction offsets from the `DISTORTION` layer | Heat shimmer / refraction. Currently dormant in the source but wired end to end. |
| Depth prepass → `frame.uSceneDepth` | Packed opaque depth at half res | Soft particles. Every particle system samples it to fade against geometry; losing it means hard-edged intersections with the floor. |

### 2d. Post-processing — deferred, not dropped

**Standing decision (D2): the post stack is still a requirement.** It is parked as a
research item because solving it is one self-contained problem — they all need the same
thing, a place to run a fullscreen pass per eye — and it shouldn't block the port.

The rule this implies for every other phase: **do not re-author anything to compensate for
the missing passes.** Keep `settings.global.glow` wired, keep `settings.post.*` wired, keep
emissive values and the `DISTORTION` layer assignments at their authored levels, and accept
that it looks flat and ungraded in the interim. Re-tuning the palette around their absence
and then re-tuning it back is the expensive mistake here.

Two consequences for §2b: `core/Layers.js` keeps `LAYER.VFX` and `LAYER.DISTORTION` — they
are not dead, just unread for now. And `CameraShake`/`ScreenFlash` stay wired even though
neither currently has an output.

Leads to investigate when we pick this up — **all unverified, highest-risk first:**

1. **Manual per-view post pass.** Render the scene to an offscreen target, run the passes,
   blit into the XR framebuffer — handling `ArrayCamera`'s per-view viewports and the
   projection layer ourselves. The path that actually preserves all four passes, because it
   restores the missing capability rather than working around it. Cost: reimplementing part
   of what IWSDK's render loop does, and holding 72–90 Hz across two views.
2. **Node-based post-processing.** Three r181 ships a `PostProcessing` class under
   `renderers/common/` for the WebGPU/node path, architecturally friendlier to XR than
   `EffectComposer`. IWSDK reports its renderer as "IWSDK WebGL", so this likely means
   waiting on IWSDK rather than something we adopt — worth re-checking each release.
3. **Ask upstream.** Whether IWSDK has a supported post-processing story planned is worth a
   direct question *before* building option 1.
4. **Per-effect fallbacks, if 1–3 all stall.** Bloom → additive glow cards in-material (the
   beam and bolt already draw additive geometry, so the idiom exists). Grade → bake the
   colour identity into materials and the IBL. Flash → a brief fullscreen tinted quad
   parented to the camera. Explicitly a fallback, not the plan: each is a per-asset art
   task rather than one pass, and none of them respond to `settings.post.*` live.

**Headset caveat to settle when we get there, not now:** vignette, grain and chromatic
aberration are conventionally avoided in VR — grain fights reprojection and aberration
fights the lenses. That is a reason to re-tune `settings.post.*` defaults for the headset,
not a reason to drop `GradeShader`. Contrast, saturation, temperature and lift/gain are
uncontroversial and carry most of the look.

For soft-particle depth specifically: IWSDK ships `DepthSensingSystem` / `DepthOccludable`,
but those occlude against the *real* world, not the virtual floor — not a drop-in
replacement. Relevant only if the stage ends up passthrough rather than a virtual room.

## 3. First person — SETTLED (D1)

The source is a third-person MOBA sandbox: an avatar at centre stage, an orbit camera, a
mouse cursor. Almost none of that framing survives contact with a headset, and **the port
goes first person.** The player *is* the caster.

What that settles:

- **Cast origin** is the player — hand for a line cast, feet for the ground-plane geometry.
  `AimController.setOrigin()` gets fed from the player rig instead of a character transform.
- **`animation/CharacterController.js` (390 lines) is out of scope.** No avatar, no rig, no
  mixer.
- **The four Mixamo FBX exports and `diffuse.png` (4.2 MB) are not ported.** This removes
  the only asset in the project with no IWSDK loader path — see §5. No FBX→GLB conversion
  is needed.
- **`settings[element].castAnim` and `CAST_ANIMATIONS` become dead config.** Leave the
  fields in `settings.js` rather than surgically removing them; they cost nothing and
  editing that file is pure risk. Just stop reading them.
- **`CharacterController.castLunge()` / `turnToward()` / `settings.character.*`** go with it.
- **`CameraShake` needs rethinking regardless.** Shaking a headset camera is a
  motion-sickness hazard, not juice. Candidates: drop it, or convert it to controller
  haptics — which is arguably the better VR translation of the same intent.

Phase 7 of §8 is therefore cut, and Phase 4's aim origin is unambiguous.

*Alternatives considered and rejected: keeping the avatar as a third-person diorama puppet
(closer to a straight port, but a strange thing to do in VR); or both, with the avatar as a
visible first-person body (most work, no clear payoff at this stage).*

## 4. Targeting: the core rework

`AimController` is well-factored for this. It emits exactly one event —
`cast(origin, direction, distance)` — which is precisely the signature `Ability.spawn()`
takes. Both the line indicator and the far-cast circle already resolve into that one
event. **Nothing in the ability layer needs to know how aiming changed.**

What changes is `_resolve()`, ~25 lines:

| Now | Becomes |
|---|---|
| `raycaster.setFromCamera(pointerNDC, camera)` | Ray from the XR controller's ray space |
| `ray.intersectPlane(GROUND_PLANE, hit)` | Same — the ground is still a plane at y=0 |
| `origin` = character feet | Player feet (or hand) via `this.player` |
| Left click confirms | Controller trigger via `world.input.actions` |
| `reveal` driven by real time so it animates while paused | Keep as-is |

Two IWSDK rules apply here and both are load-bearing:

- **Use the `RayInteractable` component, never a manual `Raycaster`.** The ground board
  should carry `RayInteractable` and the aim system should read the interaction result,
  rather than constructing its own raycaster. Verify whether IWSDK's ray gives you the
  world-space hit point directly; if it does, `_resolve()` gets *shorter*.
- **Never allocate in `update()`.** `AimController` already obeys this (`_hit`, `_flat`
  are instance fields). Preserve that when rewriting.

Ability slot selection (Q/E/R/F/V/X, six slots) has no controller equivalent. Options: a
radial/wrist-mounted UIKitML menu, thumbstick-click cycling, or two abilities bound to the
two controllers. This is a UX design task, not a porting task.

## 6. Performance

The source's own numbers (§1) are desktop, one view. On Quest 3 you are rendering twice at
72–90 Hz. Specific concerns, roughly in order of severity:

1. **The six-light pool.** `LightPool` parks six `PointLight`s in the scene permanently —
   correct on desktop (adding/removing lights forces a full material recompile), but mobile
   tile GPUs hate dynamic lights and six real-time point lights on Quest is a lot. Consider
   cutting to 2–3, or faking the light contribution in-material.
2. **`MAX_CONCURRENT = 4`.** At the ceiling the source hits ~186 draw calls. Start at 2 for
   VR and raise it only if the frame budget allows.
3. **Particles.** ~1150 live for one ice field. `settings.global.particleCount` exists
   precisely to scale this — a "VR" preset that halves count, size and emission rate is a
   one-line change through `applySettings()`.
4. **Transparency and overdraw.** Crystals are `transparent: true, depthWrite: true`, the
   snare field and targeting circle are additive. Overdraw is the classic Quest killer and
   these VFX are built almost entirely from it. Budget a fill-rate pass.
5. **Shadows.** The source flags `shadowMap.needsUpdate` once per frame because it renders
   the scene several times. Those extra passes are gone, so re-evaluate whether real-time
   shadows are worth it at all.
6. **`renderer.compileAsync()`** during boot — keep the equivalent. First-cast shader
   compile stutter is far worse in a headset than on a monitor.

Verify with `scene_get_render_stats` and the Quest performance tooling (`metavr` Perfetto
capture), not by eye.

## 7. UI

2,139 lines of DOM (`HUD`, `Editor`, `PresetManager`, `glyphs`, `styles.css`) plus
`lil-gui`. None of it renders in an immersive session.

- **HUD** (ability bar, cooldown sweeps, toasts, FPS/particle/draw-call counters) →
  a UIKitML panel. The cooldown sweep is a `conic-gradient` driven by a CSS custom
  property; UIKitML is HTML/CSS-*shaped* but is not a browser engine, so that specific
  trick will not survive — rebuild the sweep as a ring mesh or a stepped bar. Invoke the
  `iwsdk-ui` skill before authoring.
- **Editor** (1,684 lines of lil-gui bound to `settings`) → **defer.** Recommend keeping it
  as a 2D browser-only panel (IWSDK runs outside XR too, and `ScreenSpace` exists for
  exactly this), rather than rebuilding a 300-control tweak panel as spatial UI. The
  `applySettings` / `snapshotSettings` / `resetSettings` API is transport-agnostic, so a
  desktop editor driving a headset session over the dev bridge is also viable later.
- **LoadingScreen** → IWSDK owns boot; drop it.

## 9. ECS design note

One structural decision worth making deliberately at Phase 3.

The project convention is "systems use queries, never manually tracked entity arrays".
`AbilityManager` is a manually tracked array (`this.active`) of pooled plain objects.

**Recommendation: leave it as-is, inside a single `AbilityCastSystem`.** The pool is
allocation-free, it is the reason casting fifty times constructs at most a handful of
objects, and shattering it into entities buys nothing — abilities are not queried by
other systems, they are driven by exactly one. The ECS boundary belongs at the *caster*:
a `Caster` component holding the selected element and per-element cooldowns, and an
`Aimable`/`RayInteractable` ground surface. Model the things other systems need to see;
keep the VFX pool as an implementation detail of the system that owns it.

## 10. Effort shape

Not a schedule — a relative sizing.

| | Weight |
|---|---|
| Mechanical port (imports sweep, utils, settings, materials, geometry, particles) | Large but low-risk |
| Ability layer | Large, near-zero risk — it is already decoupled |
| Targeting rework | Small, high-value |
| App/loop dissolution into systems | Small, mostly deletion |
| Post stack (D2, deferred) | **Small code, large uncertainty** — the open fidelity risk |
| UI rebuild | Medium; deferrable |
| ~~Character~~ | Cut by D1 |
| Perf tuning on device | Unbounded; budget real time for it |

The honest summary: **the ability content — the reason this project exists — ports almost
untouched.** The work is in the shell around it (loop, input, camera, UI, post), and the
one genuine unknown is how these VFX read without bloom.

**Decisions made while building**

- **`IBLTexture` references the manifest asset id, not a path.** `CacheManager.resolveUrl`
  maps ids → urls and falls through for real urls, so `src: "stage-hdr"` reuses the
  manifest entry and shares one decode with `AssetManager.loadHDRTextureById`. No
  duplicate 5.7 MB load.
- **No `DomeTexture`.** The source never shows the sunrise sky — it uses the HDR for
  lighting only (`envIntensity: 0.32`) and paints a flat `backgroundColor: '#121820'`
  backdrop with fog. A retuned flat `DomeGradient` reproduces that; a `DomeTexture` would
  have put a bright outdoor sky behind a deliberately dark cinematic stage.
- **Floor is untextured on purpose.** `settings.environment.floorTexture` ships **`false`** —
  the source's default floor is procedural dark stone, not the photo maps. So the board
  uses `floorColor`/`floorRoughness` and the four maps are registered `lazy` and unused.
  Texturing it would have looked *less* like the source, not more.
- **`Ground.js`'s shader patch is deferred, not dropped.** The tint grading, radial light
  pool and sheen breakup all hang off `Environment.registerShadowCasterWithPatch`, which
  is a separate port. `StageSystem` keeps the material synced from settings each frame so
  the live-tuning invariant holds for the values that *are* wired.

**⚠ Finding: the VFX layer is invisible by default**

`DustMotes` rendered nothing on first run — entity present, `renderStats.points` **0**, no
error anywhere. Cause: every ported VFX object calls `layers.set(LAYER.VFX)` (layer 1) for
the deferred depth prepass, and a Three camera renders **only layer 0**.

Fixed with `this.camera.layers.enable(LAYER.VFX)` in `StageSystem.init()`, which keeps the
layer assignments intact per D2 rather than stripping them. `LAYER.DISTORTION` is
deliberately *not* enabled — those proxies are meant to be invisible to the main pass.

**This will bite again in Phase 3.** Every ability group is `LAYER.VFX`. If a cast fires and
nothing appears, check `renderStats.points`/`calls` before debugging the ability. Not yet
verified inside an XR session, where the `ArrayCamera` sub-cameras own their own masks.
